# Instruction00009 — 自然言語だけで動くAI自動ソフト開発（AutoDev MVP）

発行日: 2026-10-10
担当: ローカルのClaude Code
前提: `instructions/Result00007.md` と `instructions/Instruction00008.md`
結果報告: `instructions/Result00009.md`

## 最優先の目的

ユーザーが本当に欲しいのは、毎回ChatGPTにResultを貼り、次のInstructionを作らせる仕組みではない。

**「作りたいソフト」を1回だけ自然言語で伝えれば、AIが計画→小タスク化→実装→機械的テスト→別AIレビュー→修正→commit→次タスクまで進め、最後に結果を1件だけ返す**仕組みを完成させる。

現状の `tools/devloop/controller.py` は1タスク内の修正ループ、`tools/devloop/autopilot.py` は事前登録された複数タスクの順次実行に対応済み。ただし人間がInstruction群・queue.yamlを毎回用意しなければならない。**今回の仕事はこの人間の中継をなくすこと**。既存Controller/Autopilotの安全装置を再実装・撤廃せず再利用する。

形式的な整備や費用をめぐる確認作業で先送りせず、まず実際に小さなソフトが最後まで作られる動作を優先する。

## 実行順序と扱い

1. ローカル `C:\project\AI-Othello` を最新の `origin/main` と同期し、ユーザーの未コミット変更を保護。
2. `Instruction00008` の実CLIスモーク試験が未完了なら、既にユーザーが許可した試験・デバッグ（そのInstructionに書かれた範囲）を先に実施し、`Result00008.md` を保存する。利用上限で止まった場合、従量課金APIや別アカウントへ切り替えて回避しない。その後、本作業の**モックで検証できる実装部分は継続**する。
3. `Instruction00008` の試験とは別に、本指示書の作業として `Result00009.md` を保存する。既存ファイルを上書きしない。作業の番号と履歴を正確に保つ。
4. 作業範囲内の実装・テスト・通常のcommit/pushは都度承認を求めずに進める。失敗時も、原因を調査して修正し、テストし直す。

## 実装要件

### A. 1コマンドで自然言語から実行

例（実際の引数名は実装に合わせて文書化する）:

```powershell
py -m tools.devloop.autodev --repo C:\project\sample-app --request "CSVを読み、指定列の集計結果を出すCLIを作って" --execute --allow-real --commit
```

- `--request` またはUTF-8 `--request-file` で自然言語要求を受け取る。長文を扱えるファイル入力を用意する。
- 原則として**実行開始後は追加の人間メッセージ不要**。計画から実装、レビュー、再試行、次タスクまで同じ起動内で進む。
- デフォルトはdry-run。実AI起動は従来の二重承認条件に従う。ユーザーがすでに起動コマンドで実AIを明示許可した場合、**AI呼び出しごとに人間に再承認を求めない**。
- 操作対象は専用作業ブランチの使い捨てクローンを基本とする。main/masterへ監督ランナーがpush・commitする禁止事項は維持する。
- 使うAIのモデル名は設定で変更可能にし、特定バージョン名をコードに埋め込まない。

### B. AIによる作業計画生成

- 新しいplanner役を用意（Claude CodeまたはCodex CLI、設定で切り替え可能）。プロンプトはstdinで渡し、応答は**厳格なJSON Schemaなどで機械的検証**する。
- 入力: ユーザーの要求、対象リポジトリの許可された構造・README、既存仕様とテスト、設定された作業範囲。
- 出力: 目的、受け入れ条件、順序付きタスク（目安1～3件の小さなタスク）、各タスクの実装範囲・自動検証条件、未確定事項。曖昧な依頼でも合理的な最小MVPを作り、要点を計画に残す。
- 新たな課金契約・認証情報の読み出し・外部公開・運用環境変更・依存関係の無断追加・削除のような行為は計画に含めない。見つかった場合は対象タスクだけ拒否するか、安全に停止。
- 生成物は `instructions/` の未使用番号へ保存。既存の `InstructionNNNNN.md` / `ResultNNNNN.md` を上書きしない。
- Controllerのretry用番号との衝突を避けるため、既存 `max_loops` を考慮して番号を予約し、順序付きキューを自動生成。番号の空きがない場合は安全に別の区画を探す。
- plannerが返す未検証の命令・文字列は信頼できない入力として扱い、直接シェルコマンドを実行しない。
- キュー投入前に形式、ファイル範囲、上限、受け入れ条件の有無を機械的に確認する。

### C. 自動開発の本体

- 既存Autopilotへ生成したキューを渡す。Claude実装担当→Controllerの機械的pytest→Codex独立レビュー→不合格なら修正→合格なら作業ブランチへローカルcommit→次タスク、を**人間の追加指示なし**に処理する。
- 指示書・キューを生成したことで作業ツリーがdirtyになり、既存Controllerが起動不能になる問題を解消する。専用ブランチで計画ファイルを限定的にstage/commitする等、既存のgit保護ルールと整合させる。作業開始前後のGit状態をモックで検証する。
- 既に実装済みのretry、blocked、失敗テスト、保護対象、二重実行防止、再開を壊さない。
- **自走の意味は新しい仕様を無限に思いつくことではない。** 最初のユーザー要求と受け入れ条件の範囲内で修正と次タスクを進め、完了したら停止する。
- 実AIで利用上限・認証制限に達したら理由を記録して停止。使用量の上限解除、外部APIキーへの切替、グローバル権限拡大はしない。

### D. ユーザーに返すものは1つ

- `AutoDev` 実行ごとに自己完結したMarkdownのサマリーを保存する（例: `instructions/AutoDevRun00001.md`。番号や保存場所は衝突しない方式を採用）。
- サマリーには元の要求、生成した計画、実行したタスク、完了/未完了、実測したテストの件数と終了コード、レビュー判断、commit SHA、実際のAI呼び出し回数、主要ファイル、停止理由、次に人間がやるべきこと（あれば）を記録。
- 端末表示はサマリーのパス、status、commit SHA、最小限の実績だけ。長いResult・ログをユーザーにコピペさせない。
- 再開時は完了タスクを二重実行せず、既存サマリーも誤って上書きしない。

## 受け入れテスト（必須）

**実AIを呼ばないモックで以下の一連の試験を自動化する。**

1. 「小さなCLIを作る」という単一の自然言語要求から、plannerモックのJSONを検証→2件以上のInstructionを自動生成→queueを作成→Autopilotが順次実行→テスト成功→ローカルcommit→サマリー生成まで1回の起動で完了。
2. レビュー `retry` →修正→complete。次タスク用の指示番号と衝突しない。
3. plannerが不正JSON・範囲外要求・無限タスクを返した場合は実装担当を呼ばず停止。
4. 中途失敗、AI利用上限、テスト失敗、レビュー `blocked` では後続タスクを開始しない。
5. 中断・再開でタスクとcommitが二重にならない。
6. dry-runは実AI起動・計画ファイル作成・Git変更などの副作用ゼロ。
7. 既存の `tests/test_devloop.py`（62件）、`tests/test_autopilot.py`（18件）およびオセロ本体のテストが退行しない。

上記のシナリオを少なくとも1件、APIを直接呼ぶ単体テストではなく**ユーザー向けCLIを起動する実運用に近いE2Eテスト**でも確認する。ローカルのモック実行と実CLI実行を混同しない。

## 開発順序（承認待ちで細切れに止まらない）

1. Plannerのスキーマ/プロンプトと厳格な検証。
2. 結果を既存Autopilotのキュー形式へ安全に変換する接続層。
3. 自動生成InstructionとGitのcleanチェックの整合。
4. 状態保存・再開・単一の最終サマリー。
5. モックE2E→原因調査→修正→全pytestを反復。
6. `README.md` と `docs/devloop.md` に1コマンドの使い方を記載。
7. `instructions/Result00009.md` に実際のコマンド/テスト/変更/残課題を記録し、作業結果とともに通常の `git push origin main` まで完了する。

**期限優先のスコープ調整**: 上記すべてが大きすぎる場合は、まずPlanner→2タスク自動実装→単一Resultまでの通し動作を優先し、見た目や汎用的な拡張は後回しにする。単なる設計文書だけで完了にしない。

## 実AIの動作確認

- `Instruction00008` の実CLIスモーク試験で動作が確認できた接続方式を採用する。壊れていたらその原因を直す。
- AutoDev自体はまずモックE2Eで完成させる。続けて、ログイン済みCLIの通常の利用枠を使って、小さな自然言語要求からの実AI試験を作業用クローンで検討する。
- **実AIを使う追加の動作確認が今回のユーザー承認の範囲か曖昧なときは、実装とモック検証を完了させ、追加のモデル呼び出しは行わずResultに次の実行コマンドを記録する。** 試験のために勝手に別の従量課金APIを接続しない。
- いずれにせよ、1回の失敗で通常のデバッグを放棄したり、毎回人間にログをコピーさせたりしない。
