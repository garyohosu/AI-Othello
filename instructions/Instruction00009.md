## 何を作るか（これだけ）

**Pythonが審判、AIはA1～H8の一手かPASSを返すだけ。8×8のテキスト盤面を更新し、AI同士の1局を終局まで回す。**

これが顧客の最優先要望。以前のInstruction00009の「自然言語Planner」「汎用AI自動ソフト開発」「自動Instruction生成」は**撤回**。既存の `tools/devloop/` を拡張せず、Autopilot・Controller・Plannerを使わずに `main.py` の既存の `play` を直接動かす。

既存実装では `game.py`、`ai_runner.py`、`tournament.py`、`main.py` があり、モックによる対局やルール判定は通っている。**新規開発は、実CLIの接続に本当に必要な最小変更のみ**。

## 完成と判定する条件

1. 8×8の `board.txt`（UTF-8、黒 `●`、白 `〇`、空 `□`）をPythonが管理・保存。AIに盤面と手番、同一の着手指示だけを渡す。
2. **AIは着手座標またはPASSしか返さない。** 合法手一覧はAIに渡さない。反転、合法手、PASS、終局、勝敗、反則10回累積はすべて既存のPythonコードで判定する。AIの文章で盤面や審判の判断を上書きしない。
3. AI対局用CLIにファイル編集・コード実行・外部ツール権限を与えない。盤面・審判・ログの書き換えをAIが行える構成にしない。**ツール禁止が実証できないCLIを「不正不能」と呼ばない。** Codexの `read-only` はシェルの読み込み・計算を完全に禁止する意味ではないので、条件を満たすことを検証する。
4. 実際にログイン済みで利用できる**2つの実AIモデル**を選び（原則低負荷・低コストのモデル）、1局対戦させる。モデル選択や実CLIのオプションは `--help`・環境に合わせ、モデルIDを推測しない。別会社同士が難しければ同一CLIの別モデルでもよい。どちらも使えない場合は、確実に再現できる阻害要因を報告する。
5. 完走したら `board.txt`、棋譜・手番ログ、結果の勝者・石数を残す。Pythonの判定に反した着手が盤面を変更しないことを確認する。
6. CLIの利用上限、タイムアウト、認証失敗などで途中停止したら「技術的中断」として記録。自動で有料APIキーや別アカウントに切り替えたり、偽の勝者を出したりしない。

## 実行手順（作業を細分化して人間に返さない）

### 1. 現状確認とモックの完走

- `C:\project\AI-Othello` を `origin/main` と安全に同期する。未コミット変更は上書きしない。
- `RequiredSpecifications.md` と実コード、`config/models.example.yaml`、既存の `Result00008.md` を確認する。
- `py -m pytest -q tests/test_game.py tests/test_runner.py tests/test_tournament.py` を実行し、既存テストを確認。
- `config/models.example.yaml` のモック2モデルで、既存の `main.py play` から1局完走できるか実演（ゲーム用の保存場所は適切な専用ディレクトリ）。すでに動くなら書き直さない。

### 2. 実AIを使える設定を完成

- `config/models.yaml` はGit管理外で用意し、既存 `config/models.example.yaml` を最小修正。モデル名、コマンド、実際の出力形式を確認する。
- Claude Code CLI `claude -p` や他社CLIが非対話で**盤面を見て一手だけ答える**設定を試す。対局用モデルにツール・ファイル編集・コード実行は与えない。
- 起動に不要な機能追加はしない。標準入力やWindows UTF-8改行で問題が再現したら `ai_runner.py` を最小修正し、必ずモックテストも追加する（`tools/devloop/adapters.py` で解決済みの事例を参考にできる）。
- まず実AIの初期盤面1手ずつを確認し、形式と合法性をPythonで判定してログに残す。失敗したら同じ場で修正して再確認する。
- 既存の `play --allow-unrestricted` はサンドボックス未確認の**検証用途のみに限定**。禁止ツールの確認ができていなければ、本対局の結果を「不正不能・検証済み」とは扱わない。必要に応じて実証できる隔離方法を採用するが、VMや大規模基盤の新規構築はしない。

### 3. 本命: 2モデルで1局完走

- 実AIの1手テストが通ったら、既存の `main.py play --black <model1> --white <model2>` を使い**1局だけ**実行。モデルのCLI呼び出しは通常1局で約60回必要なため、利用枠の消費があることを認識する。
- `main.py` には実CLI利用時の一括確認と `--yes` が実装済み。ユーザーによる実行指示・既存の許可条件に従って開始する。1手ごとに追加の承認は求めない。
- 途中でエラーになれば終了コード・stderr（秘密値は伏せる）・ログで原因を特定し、**同じ開発セッションで修正→再テスト→再開**。既存 `play --resume` を活用して初めから無駄にやり直さない。利用上限に達したらそこで停止。
- ただし明示的なツール権限拒否や安全ポリシーによる実行拒否を回避する別経路を試みない。Result00008に記録されたdevloop起動拒否を繰り返さず、今回は**オセロ本体の直接実行だけ**を対象にする。許可が必要なら、具体的な実行コマンド1つをResultに記し、人間への往復を最小化する。

### 4. 必要なテストと事実の記録

- `py -m pytest -q` で全体の退行を確認。実CLIが成功した場合はゲームID、2モデルの実ID、実行したコマンド、終局の結果、反則・技術エラー数、保存ファイルを記録する。
- **モックが通ったことを実AIの動作成功と書かない。** 実AIが1手しか応答していなければその旨、1局完走できなければ未完走と記録する。
- `instructions/Result00009.md` を新規作成する。変更ファイル、実際に実行したテスト、実AI呼び出し回数、完了/未完了、最後に必要な操作を自己完結して書く。長文ログをチャットに貼る必要がない形式にする。
- 作業範囲の通常のコミットと `git push origin main` は自律的に実施。秘密情報・一時設定・対局データを誤ってコミットしないこと。履歴破壊やforce pushは禁止。
