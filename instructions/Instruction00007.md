# Instruction00007 — devloopを「1回起動で複数作業が進む」自走型へ

発行日: 2026-10-10
実行担当: ローカルのClaude Code
前回結果: `instructions/Result00006.md`
結果報告先: `instructions/Result00007.md`

## 背景と目的

ユーザーの不満は「Instructionを1本実行→Resultを書いて止まる→次の指示をChatGPTから手動でもらう」という人間中継にある。すでに `tools/devloop/controller.py` には実装→機械的テスト→Codexレビュー→retry（最大3ループ）の内部ループが実装され、62件のdevloopテスト（全体182件）が成功した。しかしこのControllerは **1件のタスクを終えると停止し、commit/pushも行わない**。これらは意図された安全装置であり、今回無理に取り外してはならない。

**目的: 一度だけ開始したら、事前に指定された作業キューを順に処理し、成功した作業を確定して次へ進む「監督ランナー」の最小実用版を作る。** 実AIへの問い合わせは本指示の実装作業では一切行わず、モックで閉ループを検証する。元のAI-Othello本体、既存Controllerの安全既定値を維持する。

## 必須要件

### 1. 明示的な作業キューと起動

- `tools/devloop/autopilot.py` 等に「監督ランナー」を実装する。1回のCLI起動で、**明示的に登録された順序付きの複数タスク**を連続実行できる。
- 例: `py -m tools.devloop.autopilot --repo <使い捨てクローン> --queue <queue.yaml> --config <devloop.yaml> --dry-run`。正確なCLI引数は実装に合わせて文書化。
- キューの各タスクは、存在する `instructions/InstructionNNNNN.md` のパスを明示する。**AIが未承認の機能要求やタスクを勝手に追加・実行しない**。既存の指示書や結果を上書きしない。
- Controllerのretryは自動生成した `InstructionNNNNN+1`, `+2` を使うので、**次のキュー項目と番号が衝突しない**ようにする（例: 初期番号を3以上空ける検証、各タスクの番号区画の予約）。既存の番号衝突検出を維持する。
- 完了した作業の次へ進む。 `blocked`、技術エラー、テスト失敗、レビュー形式不正、限度超過、番号衝突、禁止変更などでは**即停止し、後続キューを起動しない**。

### 2. commit/pushは独立した境界で扱う

- `Controller` 本体の「AIによるcommit/push禁止」は維持する。監督ランナーのみ、`complete` かつ機械的テストが成功し、禁止変更がない場合に限り、**限定されたGit操作で**差分とResult、必要なら自動生成されたretry指示書をcommitできる。
- 初期設定は `dry-run`、**自動commitもpushも無効**。両方を明示的に許可できる別フラグ・設定を用意する。commitせず複数タスクを走らせて衝突・汚れが発生しないよう、未commitの場合は安全に停止・次タスクへ進めない設計とする。
- 自動pushはさらに別の明示的承認が必要。**main/masterへは自動push禁止**、作業専用ブランチのみ。force push、merge、rebase、削除、`git add -A` による無差別stageは禁止。対象ファイルを検証したうえで限定的にstageする。
- そもそも実行対象は**使い捨てクローン/専用ブランチ**を基本とする。監督ランナー側で元リポジトリやユーザーの未コミット変更を破壊しない。dry-runはファイル書き込みもGit変更もAI起動もしない。

### 3. 実AI利用・費用の安全境界

- `mock` 以外のCLIを実行するには、従来の `allow_real_cli: true` と `--allow-real` 等、明示的な許可が必要。監督ランナーから迂回しない。
- ランナー全体に、**最大タスク数、総AI呼び出し数、最大ループ/タスク、最大経過時間**を設け、子Controllerを跨いで制限を守る。デフォルトは安全側。異常・割込みで止まり、ログから追跡・再開できる。
- `--max-budget-usd` をClaudeに指定できても、Codexの金額上限は保証できない。モデル呼び出し数と時間上限だけでは金額上限にならない。**総額の強制上限は未実装・保証できない**ことを明記。
- 本指示では実AI CLIの実行は0回とする。実際の有料結合テスト許可は別途ユーザー判断を要する。認証情報の記録は禁止。

### 4. 状態保存・再開・可視化

- 作業タスクごとに開始/完了/失敗、対応するInstructionとResult、テストの終了コード、レビュー判定、コミットSHA、呼び出し回数を保存する。
- 再起動時、既にcomplete・commit済みの作業を**二重実行・二重commitしない**。Git HEAD・作業ツリー・結果ファイルなどの整合性を確認し、曖昧なら自動修復せず安全停止。
- 誤った成功判定を避ける。AIの報告文だけで成功扱いにせず、Controllerの機械的検証結果を使う。
- 一目でわかる作業サマリーをローカルに出す。次の作業への移行に人間のメッセージを要しないようにする。

### 5. モックでの受入れテスト

最低限、**実AIを呼ばない**テストを追加する。
1. 2件以上の事前承認済みタスクが、1回の起動で順に `complete` → commit → 次のタスクへ進む。
2. 途中の `retry` → 修正 → complete を扱える。番号が次のキュー項目と衝突しない。
3. `blocked`、テスト失敗、技術エラー、失敗レビュー、上限超過では後続タスクを開始しない。
4. 再実行時に完了タスクを二重実行せず、ResultやGit履歴を重複させない。
5. dry-runでは副作用ゼロ。commit/pushの許可がなければ実行しない。mainへの自動pushを拒否する。
6. プロンプトのUTF-8 stdinバイト完全一致など既存62件のdevloopテストが退行しない。

テスト用の一時Gitリポジトリ・モックコマンドを利用する。本番GitHubへのpushや実AIの呼び出しをテスト内で行わない。

## 実装の進め方（細切れの承認を求めない）

1. 最新 `origin/main` と `Result00006.md` を取り込み、作業ツリー状態を確認。
2. 上記の最小ランナーを実装し、ドキュメント `docs/devloop.md` とキュー設定例を追加。
3. 新規モックテストを繰り返し実行し、失敗時は原因調査→修正→再実行まで**自律的に続ける**（作業範囲内の通常の変更について都度承認は不要）。
4. `py -m pytest -q tests/test_devloop.py`、`py -m pytest -q`、監督ランナーのdry-runを実行して結果記録。
5. `instructions/Result00007.md` を新規作成し、**変更したコード、実行したテストと成功/失敗、観測したGitの動作、未解決、次にやるべき実CLI最小試験、実AI呼び出し0回**を記載する。
6. 作業範囲内の変更とResultをコミットし、外側のClaude Codeの通常作業として `git push origin main` まで実施する（**監督ランナー自身のmain自動pushを許可する意味ではない**）。競合・予期しない差分があれば勝手に強制処理せず報告。
7. 画面の報告は **Result00007へのGitHubリンク、コミットSHA、テスト結果、実AI呼び出し0回、残課題**だけにする。ユーザーに長文のコピペを要求しない。

## 重要な制約

- 本指示を実行するClaude Code自身がコードを書き、ローカルのpytestやGit操作を行うのは許可済み。**devloop/監督ランナーからの実Claude/Codex起動は承認していない。**
- 自動的に新しい製品仕様を考えて実装する機能は今回の対象外。**事前に与えた複数の作業を1回の開始で遂行する**ことに集中する。
- 既存のControllerの安全判定を緩めてテストを通さない。ブロック時は人間の判断を待つ。
- OS設定、認証情報、グローバル許可、依存関係の大規模変更、破壊的Git操作は禁止。
